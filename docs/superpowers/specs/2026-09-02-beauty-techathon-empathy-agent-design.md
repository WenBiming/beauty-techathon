## 1. 项目定位

### 1.1 目标档位

**先保初赛过线**。初赛交付物为 PPT + 演示视频，因此一切工作以「能录出一段有说服力的演示视频」为最高优先级。决赛所需的现场 Demo 与源码 zip 是本设计的自然副产物，但不为决赛额外投入。

### 1.2 赛题要求映射

| 智能接待辅助插件 | **主模块**，见 §5 |
| 风险预警跟踪看板 | **辅模块**，功能收敛但数据全真，见 §6 |

### 1.3 痛点对照

赛题原文列出三个消费者痛点，本作品逐条正面回应：

- **信息孤岛**（「客服反复询问订单信息或此前发生的问题」）→ `timeline` 全轨迹还原，客服开口即知上下文
- **千人一面**（「强调了三遍肤质困扰，平台却只推荐爆款」）→ 售前降级模式，基于肤质/成分的适配建议
- **缺乏温度**（「明明是人工，却只收到冰冷的 AI 模板回复」）→ AI 只生成候选话术并「插入」输入框，**绝不自动发送**，人工客服保留最终控制权

| 时间跨度 | 2026-05-05 ~ 2026-05-23（19 天） | 看板做日粒度趋势 |
| 未完结工单 | **28 张**（打款 7 / 退货 8 / 物流 5 / 不良反应 4 / 补发 4） | 看板「在途待办」天然有数据 |
| 角色分布 | 客服 495 / 买家 487 / 系统推送 16 | — |
| 图片消息 | 29 条（有 `image_path`，**官方未提供图片文件**） | 需自行生成 mock 图 |

### 2.2 官方标注（ground truth）

`scene_major`（10 类）与 `scene_minor`（41 类）为官方标注，998 条消息全覆盖，是评估体系的真值来源。

- `scene_major` 分布：产品咨询 180 / 补发换货 148 / 售后退货 140 / 订单服务 136 / 物流异常 126 / 退款打款 100 / 不良反应 94 / 物流服务 45 / 会员服务 17 / 其他服务 12
- `scene_minor` 分布长尾，最高 45（漏发赠品），最低 12（好评回访）

### 2.3 承诺追踪的数据依据

对全部 495 条客服消息做时限表述扫描：

- **184 条**客服消息含时限/承诺表述，覆盖 **102/138 个会话（74%）**
- 其中带**硬 deadline** 的 67 条：`1-3个工作日`×29、`48小时内`×19、`24小时内`×10、`3个工作日内`×3、`2小时内`×3、`1小时内`×3
- 软承诺：`马上`×51、`加急`×33、`立刻`×14、`第一时间`×9、`稍后`×7

赛题原文点名「隐性服务风险难以识别与跟踪，无法形成处置闭环」——承诺逾期正是这类隐性风险，且在本数据集中**可自动检测、有真实正样本**。

### 2.4 演示金样本：买家 魏h\*\*

| 时间 | 会话 | 场景 | 关键事实 |
|---|---|---|---|
| 05-05 12:05 | S00005 | 订单服务/退款迟迟不到账 | 客服承诺「若**3个工作日内**仍未到账，我们走线下打款直接补给您」 |
| 05-07 17:32 | S00059 | 售后退货/仅退款疑似异常 | 情绪显著升级（「你是不信我？」「我平台申请仅退款，你们等着！」），开风控工单 `KOC7263722`，状态**处理中**（未完结） |
| 05-09 11:28 | S00099 | 物流服务/催发货 | 第 3 次进线；此时 05-05 的 3 工作日承诺**已逾期且无人跟进** |

该买家 3 笔订单（交易关闭 228 元 / 已发货 199 元 / 待发货 129 元），累计 556 元。

此样本同时具备：重复进线、情绪升级、承诺逾期、风控工单未闭环四类风险，是演示视频的主线。

第二演示样本：买家 姚b\*\*（3 次进线，2 张未完结工单，情绪从中性 → 正向「爱了爱了」→ 焦急），用于展示情绪趋势的双向性。

#### 2.4.1 昵称撞名核查结论（2026-09-02 实测）

M1 的昵称碰撞检查标出 2 个嫌疑买家：魏h\*\*（福建厦门 / 陕西西安）与 爱h\*\*（湖南长沙 / 福建厦门）。核查结果：

**省份确实携带身份信号，这两条不是噪声。** 全库 113 笔订单分布在 17 个省，18 个多订单买家中 **16 个的收货省市完全一致**；若地址按订单随机派发，「全部同省」的期望人数仅 1.5。因此生成器是按买家固定收货地址的，这 2 例是真实异常。

**但对话内容无法判定。** 魏h\*\* 的三个会话互不引用，且 S00099 的客服开场用的是首次问候语——这既可能是撞名，也可能正是赛题所述「信息孤岛」本身。数据无 buyer_id，无法进一步区分。

**对演示叙事的实际影响（关键）：**

| 会话 | 收货地 | 在叙事中的作用 | 是否受撞名影响 |
|---|---|---|---|
| S00005（05-05 退款不到账） | 福建厦门 | 客服承诺「3个工作日内不到账走线下打款」 | **否** |
| S00099（05-09 催发货） | 福建厦门 | 第二次进线，此时承诺已逾期 | **否** |
| S00059（05-07 空包裹风控） | 陕西西安 | 情绪升级 + 未完结风控工单 | **是**，唯一有争议的一环 |

S00005 与 S00099 **同省同市**，无论如何切分都属同一买家。且已核实 **魏h\*\* 的线下打款工单数为 0**——S00005 那句承诺从未产生任何兑现记录。因此「承诺逾期 + 重复进线 + 无人跟进」这条主线是**稳的**；只有「情绪升级」依赖存疑的 S00059。

**处置：** 主演示线改用 姚b\*\*（3 会话、收货地址全一致「重庆市」、2 张未完结工单、消费 3485 元、场景链为 预售尾款咨询 → 会员权益加赠补发 → 售后期关闭过敏退款，含不良反应红线）。魏h\*\* 的厦门部分（S00005 → S00099）保留为**承诺追踪的专项案例**，不将 S00059 与另两个会话并称同一人。

### 2.6 冒烟测试结果（2026-09-02 实测）

模型 `qwen3.8-flash`，10 个会话（含 魏h\*\* 全部 3 个会话 + 覆盖 8 个 `scene_major` 的样本），单次调用输入整段对话，要求输出结构化 JSON：

| 指标 | 结果 |
|---|---|
| JSON 解析成功率 | **10/10**，零重试 |
| `scene_minor` 准确率（41 类） | **9/10** |
| `scene_major` 准确率（直接预测） | 7/10 |
| `scene_major` 准确率（**经 minor 映射反查**） | **9/10** |
| 承诺抽取 | 全部命中，含 deadline 解析 |
| 单会话 token | 均值 **660**（in 586 / out 74） |
| 延迟 | 1.44 秒/会话 |

**关键发现：`scene_minor` → `scene_major` 是严格 1:1 确定性映射**（41 个 minor 全部只对应唯一 major，零歧义；138 个会话内部标注 100% 自洽）。因此让模型预测 major 是纯粹的错误来源——直接预测的 3 个 major 错误中有 2 个（S00005、S00030）其 minor 判断是正确的，映射反查即可自动纠正。此结论已写入 §4.3。

**次要发现：** 这批模型为混合推理模型，请求需带 `enable_thinking: False`。关闭思考链后单会话仅 660 token；若开启则成本上升一个数量级，且本任务不需要长推理。这是 §4.5 成本优化的一条具体措施。

**风险标签质量：** S00059（空包裹纠纷）自动产出「恶意仅退款风险 / 客诉升级风险 / 舆情投诉风险」三个标签，与赛题点名的风险类型直接对应。

按此推算，138 个会话跑完 L1 约需 **9.1 万 token**，成本可忽略。

### 2.5 数据坑与处理

1. **图片文件缺失**：按 `image_path` 的语义目录名（如 `mock_images/broken_pump/`）生成对应 mock 图片，路径严格对齐原字段值，使 qwen-vl 链路可跑通。
2. **纯咨询会话**：25 个会话无订单无工单，插件切售前降级模式（§5.3）。
3. **昵称脱敏**：`买家昵称` 形如 `邓e**`，是数据中**唯一的跨会话身份键**（无 buyer_id）。存在同名碰撞风险。ETL 阶段执行一次碰撞检查并输出报告：对昵称相同但订单收货地址、消费区间明显不一致的情况逐条人工核对（仅 112 个买家，可穷举）。若确认碰撞则在 DB 中手工拆分为不同 buyer_id；若无碰撞则按昵称聚合。不采用「昵称+收货省市」复合键，因为纯咨询会话可能无订单、无地址。
4. **数据为虚构 MOCK**：官方已声明，所有对外材料（PPT/视频）须保留该声明，不得暗示为真实业务数据。

## 3. 数据层设计

### 3.1 存储

SQLite 单文件 `data/app.db`。选择理由：零部署、可随源码 zip 一起提交、决赛现场断网可运行。

### 3.2 原表（1:1 映射 Excel，不做清洗）

`chat` / `orders` / `ticket_reissue`（补发换货）/ `ticket_payout`（线下打款）/ `ticket_logistics`（物流）/ `ticket_adverse`（不良反应）/ `ticket_return`（售后退货）

保留原始列名的英文映射与原值，便于溯源与举证。

### 3.3 派生表

**`buyer_profile`** — 112 行，按 `买家昵称` 聚合
> 累计会话数、订单数、消费总额、工单数、未完结工单数、历史场景分布、首次/最近进线时间、当前风险等级

**`session_summary`** — 138 行，离线 Agent 产物
> 一句话摘要、意图（major/minor）、意图置信度、情绪分(1-5)、情绪趋势、风险标签数组、建议动作数组、生成时使用的模型与 token 数

**`risk_event`** — 风险事件流，看板与插件**共用同一份**，避免两处算出不同结果
> 事件类型、等级、关联会话/买家/工单、检出方式(L0/L1/L2)、状态(待处理/跟进中/已闭环)、处理人、创建/更新时间

**`promise`** — 承诺追踪表
> 来源消息 id、承诺原文、承诺类型、抽取出的 deadline、关联工单、闭环判定结果、是否逾期

### 3.4 核心资产：`timeline` 统一事件流

将三类数据按时间归并为单一事件流，是「多源跨维度融合」的技术落点，也是「信息孤岛」的正面回答。

事件来源：
- 聊天消息（`chat.发送时间`）
- 订单事件（下单 / 付款 / 发货 三个时间戳各产生一个事件）
- 工单事件（创建 / 完成 各产生一个事件；未完结工单额外产生一个「在途」标记）
- 承诺事件（`promise` 表，含 deadline 与逾期状态）

按 `买家昵称` 可跨会话拉出该买家的**完整服务轨迹**。这是插件第一屏与看板下钻的共同数据源。

### 3.5 ETL

一次性幂等脚本 `etl/build_db.py`：读 Excel → 建表 → 灌数 → 建派生表 → 输出数据质量报告（含昵称碰撞检查）。重复执行结果一致。

## 4. Agent 编排与三级成本路由

### 4.1 整体形态

**离线批处理流水线（跑一次，138 会话）+ 在线增量 Agent（客服交互时）**

离线：
```
L0 规则层（0 token）
  → L1 qwen-turbo（全量轻分析）
  → L2 qwen-plus（仅高风险会话，预计 25~30%）
  → 写入 session_summary / risk_event / promise
```

在线：
```
缓存命中 → 0 token 直出
有新消息 → 增量更新（只送新消息 + 已有摘要，不重发全历史）
客服点「生成话术」→ qwen-plus 单次调用
```

### 4.2 L0 规则层（零 token，纯 SQL）

以下信号为确定性计算，使用 LLM 反而不准且昂贵：

- 重复进线次数、距上次进线间隔
- 未完结工单数与工单龄期
- 累计退款次数/金额、跨表多工单叠加
- **客服响应时长**：`发送时间` 精确到秒，可直接计算每轮响应间隔，超时即风险
- 是否触及不良反应（工单表直读，**最高优先级红线**）
- 承诺 deadline 是否已过（基于 L1 抽取出的 deadline）

### 4.3 L1 qwen-turbo（全量）

模型：**`qwen3.8-flash`**（专属空间无 `qwen-turbo`，flash 系为最低价档）。

单次调用输入整个会话（4~10 条消息，极短），输出结构化 JSON：

- 意图分类：**只预测 `scene_minor`（41 类），`scene_major` 由确定性映射表反查**。已验证 41 个 minor 到 10 个 major 是严格 1:1 映射、零歧义（见 §2.6），因此 major 准确率恒等于 minor 准确率，让模型直接猜 major 反而引入错误。
- 情绪分（1-5 整数）
- 一句话摘要
- 初判风险标签
- **承诺抽取**：从客服消息中抽取承诺原文与时限，转换为绝对 deadline

可靠性：JSON Schema 约束输出 → 解析失败重试 1 次 → 二次失败降级为 L0 规则结果并记录。批处理不因个别脏输出中断。

### 4.4 L2 qwen-plus（按需）

模型：候选 **`qwen3.7-plus`** 与 **`qwen3.8-max`**，最终选型由实验 2 的成本-效果帕累托决定。

触发条件：L0 判定红线（不良反应/承诺逾期/工单超期）**或** L1 情绪分 ≤ 2 **或** L1 标记高风险。

输出三项：
1. **风险归因**：为什么这个会话有风险，根因在哪
2. **处置建议**：可执行的动作清单，每项绑定一个 Agent 工具
3. **共情话术**：2~3 条候选，各标注语气（安抚/专业/致歉）

话术生成的输入包含：情绪分 + 全轨迹 timeline + **相似历史案例中客服的成功话术**（§4.7 小 RAG）。

### 4.5 成本优化（加分项的落地方式）

批处理完成后产出真实成本对比表：

| 层 | 会话覆盖 | 实测 token | 实测成本 |
|---|---|---|---|
| L0 规则 | 100% 过一遍，约 40% 就此终止 | 0 | ¥0 |
| L1 turbo | 100% | 实测 | 实测 |
| L2 plus | 25~30% | 实测 | 实测 |
| 对照：全量走 plus | 100% | 实测 | 节省比例 |

单价按运行当日 DashScope 官方价目表计算，**不预设数字**。另记录在线阶段的缓存命中率。

### 4.6 多模态（按需触发）

仅当会话含图片消息（全库 29 条）时调用 **`qwen3-vl-flash`**（高难度样本升 `qwen3-vl-plus`）：识别破损/异常类型 → 判定补发或换货 → 预填补发换货工单字段。不做全量图片分析。

### 4.7 Agent 工具集（function calling）

| 工具 | 作用 |
|---|---|
| `get_buyer_timeline(昵称)` | 拉取跨会话全轨迹 |
| `get_order(订单号)` | 订单详情与状态 |
| `list_open_tickets(昵称)` | 未完结工单及龄期 |
| `search_similar_cases(场景, k)` | 检索同场景历史会话中客服的成功话术，作为 few-shot |
| `draft_ticket(工单类型, 上下文)` | 生成预填好的工单字段 |
| `check_promises(昵称)` | 该买家的承诺闭环状态 |

`search_similar_cases` 是一个小 RAG：138 个会话中包含大量同场景下已成功处理的真实客服话术，检索出来作为 few-shot，比凭空生成更贴业务口径，且比长 prompt 更省 token。

### 4.8 演示的诚实性

离线批处理意味着演示时结果是预先算好的。**这一点在视频中明说**，并解释为生产级设计（夜间批处理 + 在线增量），因为真实客服不可能等待 8 秒。同时界面保留一个「实时重算」按钮，视频中现场点击一次，证明链路真实运行。

## 5. 接待辅助插件（主模块）

### 5.1 两条铁律

官方《客服工作台说明》原文：插件区的目的是「在不干扰核心聊天流程的前提下，为客服提供即时的决策辅助和快速操作工具」。据此：

1. **AI 只建议，绝不自动发送**。话术一律「一键插入输入框」，客服可改可删。
2. **三秒法则**：最关键信息必须在第一屏不滚动可见。

### 5.2 面板结构（右侧窄栏，自上而下）

**① 共情头卡**（第一屏，不可折叠）
> 买家昵称 + 风险徽章（第 N 次进线 / 承诺逾期 / 工单未决）+ 累计消费 + 情绪条（1-5 可视化 + 较上次会话的趋势箭头）+ 一句话摘要

**② 全轨迹时间线**（默认折叠，显示最近 5 条）
> 聊天/订单/工单/承诺四类事件混排，未完结工单与逾期承诺高亮并显示龄期

**③ 决策辅助**
> AI 判定意图 + 置信度 → **风险提示（可与表面意图不一致）** → 关键事实核对（订单状态/物流状态/退款状态，即客服最常反问的三件事）→ 建议动作清单（每项可点击，直连 Agent 工具）

卡片 ③ 是本作品的灵魂：以 魏h\*\* 为例，买家表面问「催发货」，AI 也确实识别为催发货，但系统同时提示「**真正的风险在上一单未闭环的承诺与风控工单**」。这是「共情」与「关键词匹配」的分界线。

**④ 共情话术**
> 2~3 条候选，各标语气；「一键插入」「换一批」

**⑤ 一键开单**
> 工单字段已预填，客服确认后提交

### 5.3 售前降级模式

对 25 个无订单无工单的纯咨询会话，面板自动切换为：肤质/成分适配建议、相似买家的选择参考、比价与套装搭配答疑。回应「千人一面」痛点。

### 5.4 界面实现

技术栈为纯 Python（Streamlit），实现方式：

- 三栏仿千牛外壳：`st.columns([1.2, 3, 1.8])`，对应左会话列表 / 中聊天窗 / 右插件区
- 注入自定义 CSS：隐藏 Streamlit 顶栏与页脚、压缩默认 padding、千牛蓝白配色、卡片圆角与阴影
- 插件卡片使用 `st.html` 手写 HTML/CSS 渲染，**不使用 Streamlit 默认组件**——这是观感的关键
- 字体：思源黑体 CN（PPT 模版亦要求此字体，保持视觉统一）

**已知取舍**：Streamlit 无法达到 React 的像素级还原，目标是「一眼可辨认为客服工作台」。若实测观感不足，备选方案是仅将右侧插件区替换为独立 HTML 组件，后端完全不动，改造成本低。

### 5.5 演示动线

接入 魏h\*\* 的 S00099 → 右栏 3 秒内亮出「第 3 次进线 + 承诺逾期 + 风控工单未决」→ 客服开口即命中上下文 → 一键插入共情话术 → 一键开单闭环。全程使用真实数据，不摆拍。

## 6. 风险预警跟踪看板（辅模块）

### 6.1 六类风险

| 风险类型 | 检出层 | 数据中的量 |
|---|---|---|
| 不良反应未闭环（红线） | L0 | 10 张工单，**4 张未完结** |
| 承诺逾期 | L1 抽取 + L0 判定 | 102 会话有承诺，67 条硬 deadline |
| 重复进线 | L0 | **24 个买家** |
| 工单积压超期 | L0 | **28 张在途** |
| 情绪升级 | L1 + 跨会话趋势 | 数值由 M2 批处理产出；魏h\*\* 为已确认的正样本 |
| 重复退款 / 风控异常 | L0 跨表聚合 | 数值由 M1 ETL 的跨表聚合产出；候选池为打款 13 + 退货 18 张工单 |

赛题点名的「舆情投诉、重复进线、情绪升级、重复退款」四类全覆盖；承诺逾期与不良反应未闭环为本作品自行挖掘的增量。

### 6.2 布局

- **顶部 KPI 条**：待处理预警 / 高危会话数 / 逾期承诺 / 不良反应待办 / **闭环率**
- **中部风险事件流**：按类型、等级、处理人筛选；**每行点击直达该会话的插件视图**（预警 → 处置的闭环，而非两个割裂页面）
- **右侧图表**：19 天日粒度趋势、风险类型分布、场景 TOP10
- **状态机**：每条预警 `待处理 → 跟进中 → 已闭环`，可指派、可备注

赛题要求「预警与状态跟踪……形成处置闭环」，故状态机与闭环率为必需功能。

## 7. 可量化评估体系

赛题原文明确「鼓励参赛团队提出可量化的评估标准」。四组实验，全部产出真实数字进入 PPT。

### 实验 1：意图识别准确率

真值：官方 `scene_major`（10 类）/ `scene_minor`（41 类）标注，998 条消息全覆盖。
产出：Accuracy、Macro-F1、混淆矩阵。
划分：按**会话**分层抽样切分，避免同会话消息跨越训练/测试造成泄漏（本作品为纯 prompt 方案，无训练，但 few-shot 示例的选取需排除测试集）。

### 实验 2：成本-效果帕累托

同一测试集分别用 `qwen3.8-flash` / `qwen3.7-plus` / `qwen3.8-max` 跑意图分类，绘制**准确率 vs 成本**散点图。
目的：论证三级路由是有实验依据的工程选择，而非拍脑袋。此图同时服务「模型分析准确度」与「成本优化加分项」两个评分维度。

### 实验 3：风险识别一致性

重复进线、承诺逾期、工单超期由 L0 规则算出，属确定性真值。以此为标尺校验 LLM 的风险判定，计算召回率与误报率。同时验证「该用规则的地方用规则」的架构决策。

### 实验 4：话术质量（LLM-as-judge）

三维打分：共情度 / 信息准确性 / 合规性。
对照组：数据集中客服的**真实回复**。
注意：本数据集的客服话术水准较高（如 S00082 不良反应会话），构成**强基线**。若打平或超过则说服力充足；若未打平则如实报告——真实的负结果比虚假的正结果更可信。

### 情绪判断的真值

数据集无情绪标注。方案：抽取 **50 个会话**人工标注情绪金标集（Claude 先标，用户复核，预计 30 分钟）。无此金标集则「情绪判断」无法量化，故此成本必须支付。

## 9. 非目标（YAGNI）

明确**不做**的事，避免范围蔓延：

- 不做用户登录/权限系统
- 不做真实的千牛系统对接或插件打包
- 不做模型微调（纯 prompt + few-shot）
- 不做向量数据库（138 会话规模，关键词 + 场景过滤检索已足够）
- 不做实时消息推送/WebSocket（Streamlit 轮询足够）
- 不做移动端适配
- 不做多店铺/多租户
- 不做除演示所需之外的额外 mock 数据扩充
